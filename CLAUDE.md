# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Backend for a multi-tenant accounting SaaS ("project accounting"). Node.js + Express + TypeScript + Prisma 7 (PostgreSQL via `@prisma/adapter-pg`). Companies subscribe (pay-before-use); users can belong to multiple companies with different roles per company; core domain is double-entry bookkeeping (journal entries, fiscal years/periods, chart of accounts).

## Commands

```bash
npm run dev                    # start dev server (nodemon + ts-node, watches src/)
npm run build                  # prisma generate && tsc -p . -> lib/
npm start                      # run built server (node lib/index.js)

npm run prisma:generate        # regenerate Prisma client (also runs on postinstall)
npm run prisma:migrate         # prisma migrate dev
npm run db:studio              # prisma studio

npm test                       # vitest run (unit + integration)
npm run test:unit              # vitest run --project unit
npm run test:integration       # vitest run --project integration

npx vitest run tests/unit/dateOnly.test.ts   # run a single test file
npx tsc -p . --noEmit          # type-check only (what CI runs)

npm run activate:company       # ts-node scripts/activate-company.ts — manually mark a company subscription ACTIVE
npm run storage:check          # ts-node scripts/check-storage.ts — store, read back and delete an object in the configured bucket
```

Local Postgres for dev is provided by `docker-compose.yml` (port **5433**, db `project_accounting`, user/pass `postgres`/`postgres`). Integration tests provision their own dedicated test database (see `tests/integration/globalSetup.ts`, `testDb.ts`) using `TEST_DATABASE_URL`.

The same `docker-compose.yml` runs the local object storage: the `storage` service, an S3 API emulator (Adobe S3Mock, port **9090**, any credentials, bucket `project-accounting-dev`, files kept on a volume). The server won't start without the `S3_*` variables of `.env.example`. The file tests keep to a bucket of their own in it (`tests/integration/testStorage.ts`).

CI (`.github/workflows/ci.yml`, runs on push to `main`/`niklas-dev` and PRs to `main`): `npm ci` → `tsc --noEmit` → `prisma migrate deploy` → `npm run build` → `npm test`, against a real Postgres 16 service container and an S3Mock one.

## Architecture

### Request flow
`src/index.ts` creates the HTTP server (graceful shutdown on SIGINT/SIGTERM, 10s force-exit) around the app built by `src/app.ts` — the app factory is kept separate from `.listen()` so it can be imported directly in integration tests. Middleware order: Helmet → CORS (credentials on, origin pinned to `env.CORS_ORIGIN`) → JSON body parsing (100kb limit) → cookie-parser → Morgan (non-test envs only) → routes → `notFound` → `errorHandler`.

Before any middleware, `trust proxy` is set from `TRUST_PROXY` (`src/lib/trustProxy.ts`): unset means none, otherwise a number of proxy hops or a list of proxy addresses/subnets. It decides `req.ip`, which the rate limiters count by and Morgan logs. Production behind a reverse proxy must set it, or every client shares one rate-limit bucket; "trust everything" (`true`, `/0`) is refused at startup.

Routes are aggregated in `src/routes/index.ts`: `/health`, `/api/auth`, `/api/companies`, `/api/settings/user` and `/api/invitations` are mounted outside the paywall (each does its own internal gating); every other `/api/*` route is gated behind `requireAuth` + `requirePasswordChanged` + `requireActiveSubscription`. Route → controller (Zod validation of body/params/query) → service (business logic, Prisma calls) → `AppError` thrown on failure, caught by the centralized `errorHandler` (translates `AppError`, `ZodError` → 400, Prisma `P2002` → 409, else 500 with detail only in dev).

### Auth & sessions
Cookie-based sessions, not JWT (`src/lib/session.ts`): a random 32-byte base64url token is issued to the client, but only its SHA256 hash is stored server-side, so a DB breach doesn't leak usable tokens. Sessions have a 30-day TTL with a sliding window — `lastUsedAt` is bumped (and expiry extended) once it's over a day old. `requireAuth` (`src/middleware/requireAuth.ts`) resolves the cookie to a session, attaches `req.auth = { user, session, membership }`, and **re-verifies company membership on every request** so revoking access is instant, not cached. State-changing requests (non-GET/HEAD) are checked against `Origin` matching `env.CORS_ORIGIN` as CSRF protection. Passwords are Argon2id; login uses a dummy hash comparison on unknown emails to avoid timing leaks. Email verification and password reset both use one-time tokens (`VerificationToken`, 1-hour TTL) sent via `src/lib/mailer.ts`.

**Temporary passwords.** An account a company administrator creates for someone else (see **Company users** below) gets a generated temporary password (`generateTemporaryPassword` in `src/lib/password.ts`, which also holds `hashPassword`) and `User.mustChangePassword = true`. While that flag is set, `requirePasswordChanged` answers 403 `Password change required` on everything but `/api/auth` — it sits on the gated router, `/api/companies`, `/api/settings/user` and `/api/invitations`, so add it to any new router mounted outside the gated one. The way out is `POST /api/auth/change-password` (`{ currentPassword, newPassword }`, rate limited): it verifies the current password, clears the flag and deletes the user's other sessions. A password reset clears the flag too. Nothing ever sets the flag again on an existing account. The rule for a chosen password is `passwordSchema` in `src/lib/apiSchemas.ts`.

### Multi-tenancy
`Company` has a `subscriptionStatus` (`PENDING_PAYMENT` / `ACTIVE` / `PAST_DUE` / `CANCELED`); `requireActiveSubscription` gates access accordingly. `CompanyUser` is the membership join table (composite `userId`+`companyId`, carries `role` — `VIEWER < LEDGER < ACCOUNTANT < ADMIN` — and `isAdmin`). A user can hold different roles in different companies. The role order and the rules for who may change whose role live in `src/lib/roles.ts`. Sessions track an `activeCompanyId` so "switch company" is just updating the session row.

**Signing up registers a person, not a company.** `POST /api/auth/signup` takes only the user's own details; the new user belongs to no company and their session has no active company, so the gated router answers them 403 `No active company selected`. They get a company in one of two ways: a company administrator invites them and they accept (see **Company users** below), or they register one with `POST /api/companies` (`companyService.create`; auth-only, open to any user, also one who already has companies). The creator becomes the new company's `ADMIN` and company administrator, the company starts `PENDING_PAYMENT`, and it becomes the active company of the session it was created from — all in one transaction. The details' upper bounds match those of changing them later (`company-info.controller.ts`); keep the two schemas in step.

Almost every domain table carries a `companyId` and services must filter by it; some tables (e.g. `AccountingPeriod`) denormalize `companyId` from their parent for indexed lookups.

### Settings
Settings come in two kinds, and which kind a setting is decides where it is stored and how it is gated:

- **User settings** (`UserSettings`, keyed by `userId`; `src/services/user-settings.service.ts`) describe the person — currently only the UI `language`. They follow the user into every company, so `GET`/`PATCH /api/settings/user` is auth-only (**not** subscription-gated), always acts on `req.auth.user.id`, and never looks at the active company. `/api/auth/me` returns them as `settings` so the UI can apply them at boot. The row is created lazily: no row means `DEFAULT_USER_SETTINGS`, the first `PATCH` upserts. To add one: column on `UserSettings` (+ migration) → `UserSettings`/`DEFAULT_USER_SETTINGS` in the service → the Zod patch schema in the controller.
- **Company settings** (`CompanySettings`, keyed by `companyId`; `src/services/company-settings.service.ts`) describe the company's books and apply only to the active company — currently only `vatRegistered`. `GET`/`PATCH /api/settings/company` mounts on the gated router, is scoped by `req.auth.membership.companyId` and role-checked: everyone reads (the UI needs them to know what may be entered), `ACCOUNTANT`+ changes. The row is created lazily like `UserSettings`: no row means `DEFAULT_COMPANY_SETTINGS`. To add one: column on `CompanySettings` (+ migration) → `CompanySettings`/`DEFAULT_COMPANY_SETTINGS` in the service → the Zod patch schema in the controller. The VAT accounts predate the table and stay on `ChartOfAccounts` (`/api/chart-of-accounts/vat-accounts`, `LEDGER`+ changes), and so does the trade payables account (`/api/chart-of-accounts/trade-payables-account`, see **Suppliers & purchase invoices**).

- **Bank accounts** (`BankAccount`; `/api/bank-accounts`, `src/services/bank-account.service.ts`) are managed from the UI's company settings but are rows of their own, not columns on `CompanySettings`: a name, an IBAN (unique per company, stored normalized; shape and mod-97 checksum checked by `src/lib/iban.ts`, which the UI mirrors) and the accounting account they are booked on. That account must be in a group classified as the balance sheet item `CASH_AND_BANK` ("Rahat ja pankkisaamiset"); it is checked on create and whenever an update picks a different account, so an existing link is not re-checked on a rename or when taken out of use, nor when the account or its group is reclassified later. Everyone reads, `LEDGER`+ changes. There is no `DELETE`: a bank account is taken out of use and back with `isActive` in the `PUT` body (left alone when omitted; a new one is always in use). One out of use still reserves its IBAN and still blocks deleting its accounting account.
- **Company info** (`GET`/`PATCH /api/settings/company/info`; `companyService.getInfo`/`updateInfo`, `src/controllers/company-info.controller.ts`) is the `Company` row's own details: name, business ID and the billing email and address. Everyone in the company reads them; a partial, strict `PATCH` changes them and is for company administrators (`requireCompanyAdmin`, i.e. `CompanyUser.isAdmin` — not an accounting role). The business ID is returned but is not in the patch schema, so it can't be changed.
- **Company users** (`/api/settings/company/users`; `src/services/company-user.service.ts`) are the company's members (`CompanyUser` rows): who they are, their accounting role and whether they are company administrators. Everyone in the company reads the list.
  - *Adding and removing* is for company administrators (`requireCompanyAdmin`). `POST` with an email that has no account creates one with a temporary password, returned in that response only (`temporaryPassword`) for the administrator to hand over; that person is a member at once, the account existing only because of this company. An email that already has an account (users are shared between companies) is **not** made a member but sent an invitation (next point), keeping its own name and password. The response is `{ member, temporaryPassword, invitation }`, with either the first two or the last set. `DELETE /:userId` deletes the membership, not the `User` — it may belong to other companies and its journal entries keep pointing at it — except that an account still on its temporary password with no other membership is deleted, so a mistyped email can be entered again. `POST /:userId/temporary-password` issues a new one, only while the account is still on a temporary password **and** belongs to no other company: anything looser would let one company's administrator into an account that opens another company's books.
  - *Invitations* (`CompanyInvitation`; `src/services/company-invitation.service.ts`) are how a user with an account joins: the invitation carries the role and administrator flag the administrator chose and waits in the user's inbox, `GET /api/invitations` (auth-only, outside the paywall — the user may have no company; `/api/auth/me` returns the same list as `invitations`). `POST /api/invitations/:id/accept` turns it into the `CompanyUser` and, only if the session has no active company, makes that company active; `POST /:id/decline` deletes it. The company sees its pending ones at `GET /api/settings/company/invitations` (every member) and a company administrator cancels one with `DELETE /:id`. A row exists only while pending — no status, expiry or history — and is unique per user and company. Inviting is refused (409) for a member, for someone already invited, and for an account still on its temporary password: the company that created that account can log in as its user, so it could accept for them. That refusal is also what keeps a temporary-password account in one company only, which the temporary-password rules below rely on.
  - *Changing a role* (`PATCH /:userId`, `{ role?, isAdmin? }`) has no route guard, because the answer depends on both members: the service applies `canManageMember` / `assignableRoles` from `src/lib/roles.ts`. A company administrator sets any role and the `isAdmin` flag on anyone else. Without the flag, `ACCOUNTANT` and up may change the role of a member who is not a company administrator and whose role is below their own, to a role below their own (so the `ADMIN` role, which no route requires, ranks one step above `ACCOUNTANT` here). The UI mirrors these rules in its `src/lib/roles.ts` — change both together.
  - *Nobody acts on themselves* (role, flag or removal). That is what keeps a company from losing its last administrator: only administrators can demote or remove one, and the one acting keeps their own flag. `update` and `remove` take the per-company `acquireMembersLock` (`src/lib/companyLock.ts`) and re-read both memberships inside the transaction, so two administrators acting on each other at once can't both succeed. Any new code that changes `role`/`isAdmin` or deletes a membership must do the same.

Never put a company-specific value on `UserSettings` or a personal preference on a company table. A preference that is personal *and* per company would belong on `CompanyUser`; nothing needs that yet.

### Accounting domain
- **Journal entries** (`src/services/journal-entry.service.ts`): double-entry, lines carry `debit`/`credit` amounts that must balance (compared in cents to avoid float rounding) inside a `prisma.$transaction`. Voucher numbers are allocated atomically per company+voucherType via an `upsert` on `VoucherCounter` to serialize concurrent numbering.
- **VAT** (`src/lib/vat.ts`): lines are stored net. A line with a `vatRate` gets a generated row (`JournalEntryLine.isVat`) on the VAT account `ChartOfAccounts` names for its side — `vatReceivableAccountId` for debit lines, `vatPayableAccountId` for credit lines — and the entry must balance with those rows counted. Amounts are entered net (VAT added on top) or gross (VAT taken out of the amount) per the request's `vatBasis`, which is not stored: a line's gross is its `amount` + `vatAmount`. The service derives the net amount, `vatAmount` and the VAT rows itself on every create/update; clients send only the entered lines. With `automaticVat: false` in the request no VAT rows are generated: the lines are stored and balanced as entered, the caller books the VAT as lines of its own, and `vatRate`/`vatAmount` on a line are descriptive only. The UI mirrors `vatCents` / `vatCentsInGross` to preview the rows, so change the rounding in both. A company whose `CompanySettings.vatRegistered` is off books no VAT: a line with a `vatRate` other than 0 is refused on create and update, with `automaticVat` on or off (`assertVatAllowed`); entries made while it was registered are left as they are. An account may carry a `defaultVatRate` (one of `VAT_RATES`, or null for none; 0 is a default of its own), set through the account's `PUT`. It is only a prefill for the UI: the service never derives a line's rate from its account, and the default is neither refused nor cleared for a company that is not VAT-registered — the UI simply doesn't apply it.
- **Fiscal guards** (`src/services/fiscal-guard.service.ts`): postings are only allowed on dates covered by both an `OPEN` `FiscalYear` and an `OPEN` `AccountingPeriod`. A GiST `EXCLUDE` constraint at the DB level prevents overlapping fiscal years per company (see migration `20260709204556_add_fiscal_years_and_periods`).
- Date-only columns (fiscal year/period boundaries, journal entry dates) are normalized to UTC midnight via `src/lib/dateOnly.ts` — always use it rather than raw `Date` construction when writing to these columns.
- `src/lib/defaultChartOfAccounts.ts` seeds a default chart of accounts for new companies; `AccountMainClass` enum defines the standard grouping (REVENUE, MATERIALS_AND_SERVICES, PERSONNEL_EXPENSES, etc.).

### File storage
A company's files (`StoredFile`; `/api/files`, `src/services/stored-file.service.ts`) are the documents of its vouchers. The row holds what is known about a file; the bytes are an object in a private bucket, spoken to over the S3 API (`src/lib/objectStorage.ts`): Cloudflare R2 in production, the S3Mock container in development and tests. Everyone reads (`VIEWER`), `LEDGER`+ uploads, links and deletes. The rules:

- **A file is reached only through its company.** The company is always `req.auth.membership.companyId`, never a path, query, body or form value, and a file is read by id only with the company in the `where` (`findCompanyFile`), never by id alone. A file of another company, an unknown id, a malformed id and a row whose object is missing all get the same `404 File not found` (`fileNotFound`): a file route never answers 403 for a file it won't show. The 403 of `roleAtLeast` is another matter, since it comes before any lookup and is the same for every id. A storage or database failure stays a 500; it must not look like a file that doesn't exist.
- **Storage keys are the server's.** `companies/{companyId}/{fileId}`, built only in `src/lib/storageKey.ts`, never taken from a client and never serialized (`serializeFile`). `objectStorage` is told the company with every call and refuses a key outside its prefix, and the `StoredFile_key_in_company_prefix` CHECK constraint (raw SQL in the migration, like `FiscalYear_no_overlap`) keeps a row from pointing outside its own company's prefix.
- **The bytes pass through the API both ways.** No presigned URLs and nothing public: `GET /api/files/:id/content` streams the object as an `attachment`, with the type detected at upload and `no-store`. The header comes from `attachmentDisposition` (`src/lib/contentDisposition.ts`), which writes the name as `filename*`; `res.attachment()` would send an `ä` as a raw Latin-1 byte.
- **Uploads** are multipart with one `file` field (`uploadSingleFile`, placed after the role gate so nothing is buffered for a caller without the role), at most `MAX_FILE_SIZE_BYTES`. What a file is, is decided from its first bytes (`detectMimeType` in `src/lib/fileType.ts`), not from its name or the client's `Content-Type`, and only `STORABLE_MIME_TYPES` are taken (415 otherwise). The stored name is the client's, cleaned by `sanitizeFileName`.
- **Row and object stay in step.** Upload: the object first, then the row in a short transaction; if the row can't be written, the object is deleted again. Delete: one transaction with the object's deletion as its last step, so a storage failure rolls the row back. Never hold a transaction open over an upload to storage.
- **The link to a journal entry** (`journalEntryId`, optional; given at upload or with `PATCH /api/files/:id`) makes the file part of that voucher: linking, unlinking, moving and deleting it go through `assertEntryEditable` for every entry involved, and the entry must be the company's (`404 Journal entry not found` otherwise). Deleting an entry does not delete its files: the FK is `SetNull`, and they stay with the company, unlinked.

Configuration is `S3_ENDPOINT`, `S3_REGION` (`auto` for R2), `S3_BUCKET`, `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY` (`src/config/env.ts`, all required). The client uses path-style addressing and `WHEN_REQUIRED` checksums on purpose (see `objectStorage.ts`), and only `PutObject`, `GetObject` and `DeleteObject`. `npm run storage:check` runs an object through `objectStorage` and back; run it when a bucket is first configured, because S3Mock takes any credentials and so proves nothing about an R2 configuration.

### Bank statements
A bank statement (`BankStatement`, tiliote; `/api/bank-statements`, `src/services/bank-statement.service.ts`) is a PDF the company has imported, to be booked by hand. Nothing is read from the PDF: the row knows only its file, the bank account it was chosen to be of (`bankAccountId`, null until chosen, may be one taken out of use) and `posted`. Everyone reads, `LEDGER`+ imports and changes.

- **Importing** (`POST`, multipart `file` through `uploadSingleFile`) takes a PDF only (415 otherwise; one PDF is one statement) and writes the `StoredFile` and the `BankStatement` rows in one transaction through `storeFile` in `stored-file.service.ts`, which is where the object-then-rows rule of the file storage lives — don't store a statement's file any other way. The bytes are read back through the file API (`GET /api/files/:fileId/content`); there is no download route here.
- **The file belongs to the statement.** `/api/files` answers 409 to deleting it or linking it to a journal entry (`assertNotBankStatementFile`), and leaves it out of the `unlinked=true` list. There is no `DELETE` for a statement.
- **`posted` is the user's mark** (`PATCH`, `{ bankAccountId?, posted? }`, strict), not something derived, and it locks nothing: what may be booked is decided by the fiscal guards alone. `GET /?posted=true|false` filters by it; without it the list has both.
- **Entries point at their statement** (`JournalEntry.bankStatementId`): given in the body when an entry is created (must be the company's, 400 otherwise), not in the update schema, so an entry stays with its statement — the same treatment as `voucherType`. They are created, changed and deleted through `/api/journal-entries`, listed with `?bankStatementId=`. Deleting an entry leaves the statement.
- **The summary** (`GET /:id/summary`, `src/lib/bankStatementSummary.ts`, DB-free and in cents) is what has been booked from the statement: debits (`deposits`) and credits (`withdrawals`) on the bank account's accounting account (`bank` is null while no bank account is chosen), and the VAT by rate and side from the entered lines' `vatRate`/`vatAmount` — not from the generated VAT rows, which don't know their rate and are missing from an entry booked without automatic VAT.

### Bank statement transactions
A statement's transactions (`BankStatementLine`; `/api/bank-statements/:id/lines`, `src/services/bank-statement-line.service.ts`) are imported from the bank's CSV export of the account and booked one by one. `VIEWER` reads, `LEDGER`+ previews, imports and deletes.

- **Reading the CSV** is `src/lib/bankCsv.ts` (DB-free). Finnish banks have no common CSV standard and publish none of their layouts, but they share the column vocabulary, so a column is recognised by its name (the `FIELD_NAMES` table, Finnish, Swedish and English) and, failing that, by its values. Encoding (UTF-8 with or without BOM, UTF-16, else Windows-1252), separator (`;`, tab, `,`), header row (past preamble lines) and the date and amount forms are worked out from the file. OP and Nordea's two layouts are also recognised by name (`detectLayout`), only to tell the user; the unit tests hold made-up files in their layouts. A file's columns are only ever a guess: `POST /:id/csv-preview` shows them with the rows and the UI lets the user correct them, sending them back as `mapping` (field → column indexes) with the file.
- **Importing** (`POST /:id/lines`, multipart `file` + optional `mapping` through `uploadSingleFile`) needs the statement's bank account. A row already imported to any statement of the same bank account is skipped: its `dedupeKey` is the bank's archive ID, or a hash of its details numbered by occurrence, so two identical card payments on one day both stay and the same file imported again adds nothing. Imports run under a per-company advisory lock (`acquireStatementLinesLock`). Rows that are no transactions (a pending `Varaus`, a balance row, another currency) are skipped and reported. The CSV file itself is not stored.
- **Booking**: a journal entry created with `bankStatementLineId` books that transaction. It must be the company's, on the entry's statement (taken from the transaction when the entry names none) and unbooked; the link is set in the entry's transaction with a conditional update, so a second booking gets 409. Deleting the entry frees the row (`SetNull`); a booked row can't be deleted.

### Suppliers & purchase invoices
Suppliers (`Supplier`; `/api/suppliers`, `src/services/supplier.service.ts`) and purchase invoices (`PurchaseInvoice`, ostolasku; `/api/purchase-invoices`, `src/services/purchase-invoice.service.ts`) are in `prisma/models/purchases.prisma`. `VIEWER` reads both; `LEDGER`+ does everything else, approving included.

- **Suppliers**: name, business ID, VAT number, contact details, `country` (ISO alpha-2, default `FI`), default IBAN/BIC, default account and default VAT rate. A `FI` supplier's business ID is a Y-tunnus, normalized and checked by its check digit, and its VAT number must be the one the business ID gives (`src/lib/businessId.ts`); another country's ID is free text. Business IDs are unique per company when given. The bank details, the account and the VAT rate are only prefills for the UI, like `Account.defaultVatRate`: the server never copies them onto an invoice. `PUT` is a full replace (an optional field left out is cleared). Deleting a supplier with invoices is refused (409); deleting its default account just clears the default (`SetNull`).
- **Invoices** have rows of their own (`PurchaseInvoiceLine`), not journal entry lines. Each row is one-sided: account, amount, VAT rate, cost center and description. The other side, the debt to the supplier, is implied. Rows are stored like entry lines, net with their `vatAmount` from `splitVat`, and the invoice keeps the `vatBasis` they were entered on, so that booking them gives back exactly the same cents. The supplier's invoice number is unique per supplier (409). The payment reference is a Finnish viitenumero or an RF reference, checked by its check digits (`src/lib/paymentReference.ts`). The due date can't be before the invoice date. A new invoice may have no rows; approving needs at least one. The list returns each invoice with a `fileCount`; `GET /:id` returns the files themselves.
- **Status** (`POST /:id/status`, `{ status, reason?, paymentDate? }`) follows the `TRANSITIONS` table: `NEW → APPROVED | REJECTED`, `APPROVED → PAID | NEW`, `PAID → APPROVED`, `REJECTED → NEW`. Anything else is 409. Every change, edits included, first takes the invoice's row lock (`lockInvoice`, `SELECT … FOR UPDATE`), so of two changes at once the second sees the first. Only a `NEW` invoice can be edited or have files attached; only `NEW` or `REJECTED` can be deleted.
- **Approving books it**. `bookInvoice` builds the entry with `buildPurchaseEntry` (`src/lib/purchaseInvoice.ts`, DB-free): a `PURCHASE` entry on the `entryDate`, one debit line per row (VAT rows generated as usual) and one credit line for the gross total on the chart's **trade payables account**. That account is `ChartOfAccounts.tradePayablesAccountId`, set through `GET`/`PUT /api/chart-of-accounts/trade-payables-account`; it is seeded to `2700 Ostovelat`, can't be deleted while set, and without it approving answers 400. The entry is written through `createJournalEntryInTx` in the invoice's transaction, so the fiscal guards apply to the entry date. The invoice's files become documents of the entry. **Reopening** (`APPROVED → NEW`) clears the link and deletes the entry through `removeJournalEntryInTx`, which is refused once its period is closed. `PAID` is only a mark with a `paymentDate`: the payment is booked from the bank statement as before. A CHECK constraint keeps `journalEntryId` set exactly while the invoice is `APPROVED` or `PAID`.
- **An invoice's entry is the invoice's**: `/api/journal-entries` answers 409 to changing or deleting it.
- **Files** are uploaded with `POST /:id/files` (through `storeFile`) and read through the file API. A file with `purchaseInvoiceId` is managed through its invoice: `/api/files` refuses to link it to a voucher, refuses to delete it while the invoice is approved or paid, and leaves it out of `unlinked=true`. Deleting an invoice keeps its files with the company, unlinked (`SetNull`), the same rule as for a deleted entry. An account or cost center used on an invoice row can't be deleted.
- **Reading inside a transaction**: an `include` of two to-many relations makes Prisma run two queries at once on the transaction's single connection, which pg deprecates. So the invoice is read back after the transaction commits (`readInvoice`), and the list includes only the rows and a count of the files.

### Prisma setup
This is **Prisma 7**: the connection URL lives in `prisma.config.ts` (not `datasource.url` in schema), and the client is generated into `src/generated/prisma/` (gitignored; regenerated on `postinstall` — run `npm run prisma:generate` after `prisma:migrate`, which no longer does it) and used through `@prisma/adapter-pg` rather than Prisma's bundled query engine. The schema itself is split into topic files under `prisma/models/` (`auth.prisma`, `users.prisma`, `companies.prisma`, `accounting.prisma`, `fiscal.prisma`, `storage.prisma`, `purchases.prisma`) with `prisma/schema.prisma` only holding generator config — edit the relevant model file, not schema.prisma directly. `src/lib/prisma.ts` exports a singleton client stashed on `globalThis` so it survives nodemon reloads.

### Validation & error handling
Zod schemas live alongside their controllers (reusable primitives like `dateOnlySchema`, `idParamsSchema` are in `src/lib/apiSchemas.ts`). Controllers validate and hand parsed input to services; services never see raw request objects. Async route handlers are wrapped in `src/lib/asyncHandler.ts` so rejected promises reach `next(err)` instead of crashing the process. Throw `AppError` (`src/lib/AppError.ts`, carries an HTTP status + `isOperational`) for any expected business-logic failure rather than a plain `Error`.

### Tests
Unit tests (`tests/unit/`) cover pure logic (date normalization, chart-of-accounts seeding, period generation) with no DB. Integration tests (`tests/integration/`) run against a dedicated provisioned Postgres database, execute **sequentially** (`fileParallelism: false` in `vitest.config.ts`) since they share that DB, and use a 30s test / 60s hook timeout. `tests/integration/helpers.ts` has shared setup utilities (e.g. creating an authenticated request context). Those helpers insert a session directly and give their users an unusable password hash, so a test that needs a real login creates its user through `POST /api/settings/company/users` (see `auth-password.test.ts`). The rate limiters are live in tests and count per test file: keep calls to `/api/auth/login` and `/api/auth/change-password` under 10 a file.

`tests/integration/files.test.ts` needs the `storage` container (`docker compose up -d`): it uploads through the real S3 API and looks into the bucket on its own with the helpers of `testStorage.ts`. `setupEnv.ts` sets the `S3_*` variables for every integration test file, so the app under test never uses the bucket named in `.env`. A storage failure is produced with `vi.spyOn(objectStorage, ...)`.
